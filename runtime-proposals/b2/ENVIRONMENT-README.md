# Separately approved temporary SDK/KVM preparation

This continuation uses the same f1e6722920871280645fcbbeb5e03b3d4577d7b2 APK pair, certificate, compiled manifests and original harness. The earlier 36998104813 attempt stopped before Android execution. Its evidence is immutable. The parent relayed new approval “允许” (Slack message 1790939604.094629) for this temporary environment preparation and the same single P7/P8/P9 sequence; owner self exits remain two and worker one.

Only Google official `emulator` and `system-images;android-33;default;x86_64` are downloaded with the cached sdkmanager, stable channel 0 and stdin EOF. Cached command-line tools, platform-tools, build-tools 36.0.0 and already accepted licenses are copied into a new sibling SDK root. License collection and bytes must remain identical; no new terms are accepted. Google catalog XML, selected revision/archive source/checksum, actual installed metadata and tool hashes are retained. Extra dependencies/packages or any preparation failure stop the job. The SDK cache and Android/Java user cache are not modified; HOME is not repurposed.

KVM is unchanged when the job already has rw access. Otherwise the wrapper temporarily changes only the owner of the verified original `/dev/kvm` character device to this job UID. This grants node-owner control as well as rw access; the wrapper uses that authority only for granting and restoring ownership. Group, mode, ACL and other xattrs are checked through privileged read-only metadata collection, with attribute lengths and hashes retained. Recovery of the granted owner is separate from full metadata acceptance: if other metadata drifts, the verified original character-device identity and current job UID still permit revoking our owner grant; the drift remains FAILED and no other fields are repaired. ctime may change and is not represented as restored. The pathname operation between identity checks is not an atomic inode binding. A replacement node or unknown owner is never repaired.

The wrapper calls the frozen harness once as a child and retains its own finally cleanup. Preparation failure before invocation permits deletion only of the verified private SDK root. After invocation, deletion additionally requires real owned emulator/ADB stop and wait0, owned serial absence, and removal of the original private harness root. Unknown cleanup retains diagnostics and fails; KVM restoration alone does not prove open descriptors have stopped. Shared caches, other devices and persistent permissions remain outside the scope.

`environment-preparation.json` records the overall preparation and cleanup result. The original harness result is retained separately as `harness-result.json`; an outer cleanup failure overrides an otherwise passing harness. The original `cached-image.json` wording about no provisioning applies only to the frozen harness. It does not describe the whole job, which is now explicitly authorized to provision these two packages.

Neither preparation success nor copying an APK is Binder connection evidence. Actual per-case instrumentation, PID/UID/process and callback records, APK pullback identity, self-exit tokens and teardown receipts determine runtime results. The test boundary remains synthetic private Java arrays and Binder callbacks; it does not prove OS memory erasure or a production VPN connection. Failure stops without a retry or another device.
